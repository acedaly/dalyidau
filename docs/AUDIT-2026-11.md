# daly.id.au audit and findings register (November 2026)

Audit of `main` at `a0acdac` on 14 Nov 2026: the repository, read-only requests to the live site, and three
read-only reviews (security, the public site, the Payload workflow). This file is the register: what was found,
how sure we are, and where each finding is fixed. It is updated as each phase lands.

**Verified** means the code path was read end to end or the behaviour was reproduced. **Potential** means it
depends on something that couldn't be seen from here (a Cloudflare setting, a browser).

No critical findings: nothing was exploitable without signing in as an owner or admin, and no data was at risk.

How the redirect change is stored: while a page or project is off the site, its `page-redirect:*` /
`project-redirect:*` rows in `meta` hold a marker (`@page:<id>`, `@project:<id>`) instead of an address. A marker
can never be a real address, so the readers find nothing there and answer 404. For posts, `slug_redirects` rows
(keyed by the post's id) are simply kept, plus one for the address it was unpublished from. Rolling the code back
leaves these rows in place and harmless: the old page and post readers answer 404 for them; the old project
reader would redirect such an address to a URL that then answers 404.

### Found by the review pass and fixed before the PR

- Page and project redirects were kept by address, so another item taking an unpublished item's last address
  would have inherited its older addresses. They are now kept per item (the markers above), with tests.
- Duplicating an imported post copied its stored HTML: Payload fills a refused group's fields from the source
  document. Every field inside `legacy` now carries the rule too (checked against real Payload).
- `/%73hell.html` and `//shell.html` slipped past the template block; paths are now compared decoded.
- A permanently deleted item left its kept addresses behind; `forget` releases them (only on a real delete).
- Two tests proved less than their names said and were tightened (one-batch write; the "disguised PNG" label).

### Asked for at review (14 Nov) and done before merging

- **The project list race is gone, not just self-correcting.** The list is now rebuilt by one SQL statement that
  runs last in the same D1 batch as the change, so it reads the rows as that batch left them. D1 runs a batch as one
  transaction and one write at a time, so two publishes at the same moment can't each write a list missing the
  other. `test/projects.test.ts` holds four publishes until all have finished reading and then lets them write; it
  fails on the earlier version. The readers sort the list themselves.
- **Images are checked for structure when they're published** (`worker/lib/image.ts` `imageProblem`, used by
  `storePublicImage`). Before, only the type label and the size in bytes were checked, so a file that merely began
  like an image, or was cut short, was copied to the public bucket as it was. Now a file must be whole and
  well-formed for its type (PNG chunks through to IEND; JPEG frame header and end marker; GIF trailer; WebP chunks
  that fill the file, with the picture's own start code; AVIF boxes with an AVIF brand and its metadata) and at
  most 20,000 pixels a side and 100 megapixels. A post, page or project whose featured image, cover or screenshot
  fails is refused with nothing written. `test/image-validation.test.ts`. Checked against 1,174 real PNGs and 223
  generated JPEG, GIF, WebP and AVIF files: none wrongly refused (13 iOS-only "CgBI" PNGs, which browsers can't
  show, were rightly refused).
- **CI:** the browser check failed on the first push because Chrome, over the test's plain http, logs that it
  ignores the new Cross-Origin-Opener-Policy header. The check now excuses that one notice (the header is honoured
  on https). This check hadn't been run locally before the first push; it has now.

### Known limits of Phase 1

- **The image check is structural, not a decode.** A file that is whole and well-formed but whose compressed
  picture data is corrupt passes, and shows as a broken or partial picture. Nothing on the server decodes images,
  so the exposure is the visitor's browser decoding it in its own sandbox, as for any image on the web. AVIF's
  pixel size isn't read, so the megapixel limit doesn't apply to AVIF. Phase 3 resizes images at publish time: from
  then only pixels the server itself decoded and re-encoded are published, which closes this fully.
- The check runs when something is published, not at upload: a damaged file can sit in the media library (private,
  served sandboxed) until a publish that uses it is refused. An inline image in the text that fails is left out of
  the page rather than refusing the publish (audit M3, Phase 2).
- H3 (Payload saved, site not updated) is unchanged apart from the project list. It is Phase 2's main work.
- HSTS has no `includeSubDomains` (L4): the owner's call.

## Phase 2a in detail (publishing reliability, no schema change)

**H3: Payload and the site can no longer drift apart silently.** Payload saves in its own database and its hooks
then copy the published version to the site's database. The two can't share a transaction, so three things now
stand between a failed copy and a site that is quietly wrong:

| Layer                  | What it does                                                                                                                                                                                                                                                                                                                                                       | Where                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Check before saving    | The publishers have a `check` mode: every refusal a publish would give (an address in use, an unreadable or damaged image, no content, another publisher's row) and nothing written. Posts, pages and projects run it in `beforeChange`, so a publish that can't succeed is refused while nothing has been saved.                                                  | `worker/blog/payload-publisher.ts` `PublishMode`, `poc/payload/src/site/publishing.ts` `checkPage` / `checkProject`, `Posts.ts`                 |
| Retry, then say so     | The copy to the site is tried three times. If it still fails, the editor is told that Payload has the change and the site doesn't. A failed menu refresh after a page change is no longer only logged.                                                                                                                                                             | `publishing.ts` `writeToSite`                                                                                                                   |
| Sync check + Republish | `siteDrift` compares Payload's published documents with the site, from the two databases alone (it never starts Payload). The cron runs it every 15 minutes and logs `site_out_of_sync`; the dashboard's "Website sync" panel runs it live and names what's missing, stale or shouldn't be there; Republish publishes those again through the same code as saving. | `worker/site/sync-check.ts`, `poc/payload/src/site/sync.ts`, `src/views/dashboard-site-sync.tsx`, `/api/globals/site-settings/{sync,republish}` |

**H5: draft preview.** The Preview button on a post, page or project builds the latest saved version through the
publishers' `preview` mode (same validation and escaping; nothing public written; no address claimed), keeps the
result under a private key in the site's database and opens it at `/portal/preview/draft/<kind>/<id>`, rendered by
the same components as the public page, with a "Draft preview" notice. Owners and admins only; never cached or
indexed. Its images are kept under a private bucket prefix (`preview/`) that the public `/media` route doesn't
serve; the same people can load them. Previews last a day and the cron removes old ones.
`worker/site/preview.ts`, `publishing.ts` `previewEndpoint`.

Proof: `test/site-sync.test.ts`, `test/draft-preview.test.ts`; against real Payload, `e2e-platform/site.mjs`
(P1 refusal before saving, P2 sync check and Republish on a deliberately broken site, P3 preview) and
`custom-view.mjs` (the dashboard panel and a real click on Republish).

### Limits of Phase 2a

- The preview shows the last **saved** draft. There is no autosave yet (M12), so save the draft, then press Preview.
- The sync check covers posts, pages and projects (and the project list). The homepage, navigation and site
  settings are each written in a single batch with no separate index, and aren't compared.
- A write that fails all three tries still leaves Payload ahead of the site until Republish (or the next save).
  That is now visible (the editor's message, the dashboard, the log) rather than silent; it can't be made
  impossible while Payload and the site are separate databases.
- Whether Access's sign-in cookie reaches `/media/*` in production (it isn't an Access path) decides whether
  preview **images** show for the editor; the preview page itself is under `/portal`. To be checked live after deploy.
