# daly.id.au audit and findings register (November 2026)

Audit of `main` at `a0acdac` on 14 Nov 2026: the repository, read-only requests to the live site, and three
read-only reviews (security, the public site, the Payload workflow). This file is the register: what was found,
how sure we are, and where each finding is fixed. It is updated as each phase lands.

**Verified** means the code path was read end to end or the behaviour was reproduced. **Potential** means it
depends on something that couldn't be seen from here (a Cloudflare setting, a browser).

No critical findings: nothing was exploitable without signing in as an owner or admin, and no data was at risk.

How the redirect change is stored: while a page or project is off the site, its `page-redirect:*` /
`project-redirect:*` rows in `meta` hold a marker (`@page:<id>`, `@project:<id>`) instead of an address. A marker
can never be a real address, so the readers find nothing there and answer 404. For posts, `slug_redirects` rows
(keyed by the post's id) are simply kept, plus one for the address it was unpublished from. Rolling the code back
leaves these rows in place and harmless: the old page and post readers answer 404 for them; the old project
reader would redirect such an address to a URL that then answers 404.

### Found by the review pass and fixed before the PR

- Page and project redirects were kept by address, so another item taking an unpublished item's last address
  would have inherited its older addresses. They are now kept per item (the markers above), with tests.
- Duplicating an imported post copied its stored HTML: Payload fills a refused group's fields from the source
  document. Every field inside `legacy` now carries the rule too (checked against real Payload).
- `/%73hell.html` and `//shell.html` slipped past the template block; paths are now compared decoded.
- A permanently deleted item left its kept addresses behind; `forget` releases them (only on a real delete).
- Two tests proved less than their names said and were tightened (one-batch write; the "disguised PNG" label).

### Asked for at review (14 Nov) and done before merging

- **The project list race is gone, not just self-correcting.** The list is now rebuilt by one SQL statement that
  runs last in the same D1 batch as the change, so it reads the rows as that batch left them. D1 runs a batch as one
  transaction and one write at a time, so two publishes at the same moment can't each write a list missing the
  other. `test/projects.test.ts` holds four publishes until all have finished reading and then lets them write; it
  fails on the earlier version. The readers sort the list themselves.
- **Images are checked for structure when they're published** (`worker/lib/image.ts` `imageProblem`, used by
  `storePublicImage`). Before, only the type label and the size in bytes were checked, so a file that merely began
  like an image, or was cut short, was copied to the public bucket as it was. Now a file must be whole and
  well-formed for its type (PNG chunks through to IEND; JPEG frame header and end marker; GIF trailer; WebP chunks
  that fill the file, with the picture's own start code; AVIF boxes with an AVIF brand and its metadata) and at
  most 20,000 pixels a side and 100 megapixels. A post, page or project whose featured image, cover or screenshot
  fails is refused with nothing written. `test/image-validation.test.ts`. Checked against 1,174 real PNGs and 223
  generated JPEG, GIF, WebP and AVIF files: none wrongly refused (13 iOS-only "CgBI" PNGs, which browsers can't
  show, were rightly refused).
- **CI:** the browser check failed on the first push because Chrome, over the test's plain http, logs that it
  ignores the new Cross-Origin-Opener-Policy header. The check now excuses that one notice (the header is honoured
  on https). This check hadn't been run locally before the first push; it has now.

### Known limits of Phase 1

- **The image check is structural, not a decode.** A file that is whole and well-formed but whose compressed
  picture data is corrupt passes, and shows as a broken or partial picture. Nothing on the server decodes images,
  so the exposure is the visitor's browser decoding it in its own sandbox, as for any image on the web. AVIF's
  pixel size isn't read, so the megapixel limit doesn't apply to AVIF. Phase 3 resizes images at publish time: from
  then only pixels the server itself decoded and re-encoded are published, which closes this fully.
- The check runs when something is published, not at upload: a damaged file can sit in the media library (private,
  served sandboxed) until a publish that uses it is refused. An inline image in the text that fails is left out of
  the page rather than refusing the publish (audit M3, Phase 2).
- H3 (Payload saved, site not updated) is unchanged apart from the project list. It is Phase 2's main work.
- HSTS has no `includeSubDomains` (L4): the owner's call.

## Phase 2a in detail (publishing reliability, no schema change)

**H3: Payload and the site can no longer drift apart silently.** Payload saves in its own database and its hooks
then copy the published version to the site's database. The two can't share a transaction, so three things now
stand between a failed copy and a site that is quietly wrong:

| Layer                  | What it does                                                                                                                                                                                                                                                                                                                                                       | Where                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Check before saving    | The publishers have a `check` mode: every refusal a publish would give (an address in use, an unreadable or damaged image, no content, another publisher's row) and nothing written. Posts, pages and projects run it in `beforeChange`, so a publish that can't succeed is refused while nothing has been saved.                                                  | `worker/blog/payload-publisher.ts` `PublishMode`, `poc/payload/src/site/publishing.ts` `checkPage` / `checkProject`, `Posts.ts`                 |
| Retry, then say so     | The copy to the site is tried three times. If it still fails, the editor is told that Payload has the change and the site doesn't. A failed menu refresh after a page change is no longer only logged.                                                                                                                                                             | `publishing.ts` `writeToSite`                                                                                                                   |
| Sync check + Republish | `siteDrift` compares Payload's published documents with the site, from the two databases alone (it never starts Payload). The cron runs it every 15 minutes and logs `site_out_of_sync`; the dashboard's "Website sync" panel runs it live and names what's missing, stale or shouldn't be there; Republish publishes those again through the same code as saving. | `worker/site/sync-check.ts`, `poc/payload/src/site/sync.ts`, `src/views/dashboard-site-sync.tsx`, `/api/globals/site-settings/{sync,republish}` |

**H5: draft preview.** The Preview button on a post, page or project builds the latest saved version through the
publishers' `preview` mode (same validation and escaping; nothing public written; no address claimed), keeps the
result under a private key in the site's database and opens it at `/portal/preview/draft/<kind>/<id>`, rendered by
the same components as the public page, with a "Draft preview" notice. Owners and admins only; never cached or
indexed. Its images are kept under a private bucket prefix (`preview/`) that the public `/media` route doesn't
serve; the same people can load them. Previews last a day and the cron removes old ones.
`worker/site/preview.ts`, `publishing.ts` `previewEndpoint`.

Proof: `test/site-sync.test.ts`, `test/site-settle.test.ts`, `test/draft-preview.test.ts`; against real Payload, `e2e-platform/site.mjs`
(P1 refusal before saving, P2 sync check and Republish on a deliberately broken site, P3 preview) and
`custom-view.mjs` (the dashboard panel and a real click on Republish).

### Found by the independent review (14 Nov) and fixed before the PR

No high-severity finding. Each of these has a test that fails on the code as it was.

- **Every existing post would have read "stale" after the deploy.** The check compares a post with the Payload
  save it was made from (`posts.source_updated_at`), which earlier releases filled with the article's own date.
  The first check after the deploy now adopts, once, each post that was in step by the rule in force until then
  (same address, written at or after Payload's last save) by stamping it with that save; anything else is still
  reported. Nothing public changes (`sync-check.ts` `adoptEarlierPosts`, flag `site:posts-adopted` in `meta`).
- **Payload reuses a deleted page's or project's number** (its tables don't use AUTOINCREMENT), and the site
  knows pages and projects by that number. A new document given a lost document's number could have had the
  earlier one's page taken down by Republish, or replaced and redirected by a publish. A snapshot made before
  a document was created is now an earlier document's: the check lists it as having no document (left alone),
  unpublishing the new document touches nothing, and publishing it is refused until an owner has removed the
  earlier one. (AUTOINCREMENT was considered for Phase 2b and rejected: see there.)
- **A rename that overlapped an unpublish could leave the page public** with nothing able to remove it, and two
  overlapping renames could leave a second copy at another address. Taking a page or project down now removes
  every snapshot carrying its id, in the same batch; publishing removes any other copy and leaves its address
  redirecting; the check reports a second copy as stale.
- **Republish counted an item as fixed if nothing threw.** It is fixed only if the comparison, made again, no
  longer lists it; otherwise it is reported as failed, with why.
- **Removing an orphan could say "it wasn't removed" after removing it** (the menu refresh failed afterwards).
  The removal is reported as done, with a warning. The kept copy now includes the item's old addresses, has its
  own key per removal (`removed:<kind>:<id>:<when>`, never overwritten), and the addresses are released.
- **A publish refused after Payload had saved read as "not saved".** It now says "Saved in Payload, but not
  published on the website: …" and is recorded under "Last save the website missed".
- **A menu left behind by a failed refresh had no repair button** while the panel said "matches". Republish is
  offered whenever a save has missed the website since the last repair.
- **A check made after a Republish was recorded as the automatic check, two minutes in the future.** Checks made
  for a person count every save, carry the real time, and leave "Last automatic check" alone.
- **Tests:** the retry and settle loops are now in `worker/site/settle.ts`, free of Payload, with their own
  tests (`test/site-settle.test.ts`: overlapping syncs end on the latest version; a failed read is never "gone";
  a retry after a lost answer is safe). The "refuses what the publish would refuse" test now runs the publish too.

### Limits of Phase 2a

- The preview shows the last **saved** draft. There is no autosave yet (M12), so save the draft, then press Preview.
- The sync check covers posts, pages and projects (and the project list). The homepage, navigation and site
  settings are each written in a single batch with no separate index, and aren't compared.
- A write that fails all three tries still leaves Payload ahead of the site until Republish (or the next save).
  That is now visible (the editor's message, the dashboard, the log) rather than silent; it can't be made
  impossible while Payload and the site are separate databases.
- Whether Access's sign-in cookie reaches `/media/*` in production (it isn't an Access path) decides whether
  preview **images** show for the editor; the preview page itself is under `/portal`. To be checked live after deploy.

Design decisions:

- **Redirects is a global, not a collection**, so its API is under `/api/globals`, which Cloudflare Access already
  covers. No Access change is needed.
- **A hand-kept redirect is only used when nothing else answers the address.** It can never hide a live page.
- **AUTOINCREMENT was rejected.** It would stop SQLite reusing a deleted row's number, but Payload can only turn it
  on by rebuilding all 22 of its tables (copy, drop, rename), and D1 runs a migration statement by statement with
  no transaction. The reuse is handled in the publisher instead (2a review, and `forgetEarlierDocument`).

### Migrations (apply only with the owner's approval)

| Database                     | Migration                                       | What it does                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Payload (`dalyidau-payload`) | `20261114_031432_phase2b_seo_redirects_history` | 8 new tables (`redirects`, `redirects_items` and the version tables for Redirects, Navigation and Site settings), new nullable columns (`seo_*` on posts, pages, projects and their version tables; `changed_by` on `navigation` and `site_settings`) and their indexes. - **Rehearsed** on a restored copy of production (backup of 12 Nov, 33 tables): `node scripts/payload-migration-rehearsal.mjs <backup>`
  restores the backup locally, runs Payload's own migration runner and compares every existing table row for row
  and value for value. All intact; integrity and foreign-key checks pass. Run it again on a fresh
  `npm run payload:backup` just before deploying.
- **Rollback is a code rollback.** Both migrations are additive, and the earlier code neither reads nor writes
  the new tables and columns, so they are simply left in place. **Never run the Payload migration's `down`** in
  production: it drops the new tables (losing any redirects and history saved since) and rebuilds others.
- **Not reversible without loss:** only the `down` above. Nothing in `up` is.
- **Order:** deploy (site migration, then code), then open `/admin` once (Payload migration). Until `/admin` is
  opened the public site is unaffected: it reads published snapshots, and the sync check skips the redirect
  comparison while Payload's table doesn't exist.

### Found by the independent review of Phase 2b and fixed before the PR

- **High: restoring an earlier version of Redirects, Navigation or Site settings would have published an empty
  list, an empty menu or the built-in default settings.** Payload's restore of a global runs no `beforeChange`
  hook and hands `afterChange` the version row instead of the document. A restore is now followed at once by
  an ordinary save of what was restored (`poc/payload/src/site/restore.ts`): it is validated, records who
  restored it, and publishes the real document. The Homepage had the milder form of this since it was built
  (a restore changed Payload and not the site); it is fixed the same way. `site.mjs` restores all four.
- **A restore was recorded against whoever made the version, not whoever restored it.** Fixed by the same save.
- **The sharing-image columns had no `ON DELETE`**, so deleting an image ever used as one would have been
  refused. The migration now says `ON DELETE set null` on those six columns (the one hand edit to it).
- **A loop or chain could hide behind a full daly.id.au address or a `?query`.** Destinations on this site are
  compared as paths.
- **The redirect comparison looked only at dates.** It now compares the enabled rows in Payload with the list
  on the site, and reports a list the site still has after Payload's has gone.
- **Giving an imported post back to its earlier publisher left Payload's search settings on it.** Cleared.
- A redirect's old address is stored percent-encoded (as the Worker sees it), and a redirect is sent with a
  one-hour cache lifetime so removing one takes effect in browsers that had followed it.

### Found by the automated review on the PR and the second independent review, and fixed

- **A redirect to an address like `/日本` answered an error instead of redirecting** (a header can only carry
  single-byte characters). Destinations are stored percent-encoded and the header is always built through `URL`.
- **`/blog/hello` → `/blog/HELLO` looped**, because the router sends a blog address to lower case before anything
  is looked up. Old addresses and destinations are compared, stored and looked up in the form the router leaves
  them in (`routedPath`), which also makes old blog addresses containing `+`, `&` or lower-case escapes match.
- **A restore whose follow-up save was refused was left half-applied** (Payload's database has no transactions
  here). A version is now checked, exactly as a save would be, before Payload restores it
  (`checkBeforeRestore`): a list with a redirect from an address a page has since taken, or a menu linking to a
  page since deleted, is refused while everything is still as it was. `site.mjs` covers both.
- A restored Homepage draft is saved again as a draft (it was validated as if published).
- A destination that only becomes another site's address once resolved (`/a/..//host`) is refused when saved.
- The length limit on an old address is applied once, to the stored form.
- The list a redirect write replaces is kept, one back (`site:redirects-previous`).

### If the Payload migration stops part-way

D1 runs it statement by statement with no transaction, so a failure in the middle leaves some of the new
tables and columns in place and the migration unrecorded; `/admin` then fails to start ("already exists")
until it is put right. The public site is unaffected throughout (it never starts Payload). To recover:

1. `npx wrangler d1 time-travel restore dalyidau-payload --timestamp=<just before the deploy>` (nothing can have
   been edited in between, because `/admin` wasn't starting). The site's own database is not touched.
2. Find the cause in the Worker's log (`payload migrate` prints the failing statement), fix it, rehearse again
   with `scripts/payload-migration-rehearsal.mjs`, and open `/admin` once more.

Or roll the code back (`wrangler rollback`): the earlier code ignores whatever part was created.

### Limits of Phase 2b

- Redirects match the path only (no query strings, no wildcards). Outside the blog an address is matched exactly
  as typed (`/Old` and `/old` are different addresses); a blog address is matched in lower case, as the site
  serves it, and only on daly.id.au, not the wedding host. Each address that nothing answers costs one
  extra small database read.
- The homepage (a global) has no SEO group of its own: its title and description are in Site settings and Homepage.
- Versions record who and when; the admin's version comparison shows what changed. There is no separate audit page.
